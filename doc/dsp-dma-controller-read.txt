DMA controller reads beside program prefetch

The connected original voice-list service reaches MOVEP X:ffffef,A at P:00043e
while F2 owns P:00043f. These are a DMA controller register and a program fetch,
not two accesses to the same RAM. The frontend now admits real read effects
in X space when DspDma::handles identifies the controller register. Atomic bit
effects and writes do not acquire that permission. The native I/O interface
still performs the actual transaction and reports unknown/unsupported state.
Reference: DSP56300FM chapter10 register map and MOVEP/MOVE instruction entries.

The existing reference cycle orders actual DMA progress before F2/native work.
A held destination leaves DSR/DDR unchanged; its real commit updates them before
the native read. The already captured DMA payload survives a later RAM-source
write. Subsequent DMA completion cannot change a native operand already read.
Program-fetch contention and global stalls still use the ordinary bank model.
This is an explicit functional ordering, not a measured silicon bus phase.

The authored matrix checks all 29 controller words with MOVE X:ea,X0 and
MOVEP X:pp,A: 174 known cases cover quiet, held and committed transfers; 44 omit
individual preloads and 2 expose the genuinely unspecified repeating DTD state.
Every case executes on the native core and has same/fresh-owner continuations:
220 cases plus 440 restores per sanitizer. Literal register values, full CPU/
flags, accumulator sign extension, real DMA payloads, actual clocks and F2
capture are checked. Unknown reads retain the exact native I/O failure and PC.
