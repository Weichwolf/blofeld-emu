Read-only emulator design comparison

Source identities: emulator-comparison-reference.json. Gearmulator is cloned at
~/Git/gearmulator as a reference only. Do not copy its implementation into this
project or our independent DSP core. This comparison qualifies the inspected
source, not those projects' complete instrument or hardware equivalence.

Virus / Osirus
The project replaces the original i8051 controller with a C++ protocol/state
implementation. Original DSP code performs synthesis; the host implementation
handles presets, MIDI, HDI08 and initialization. Its scope is different from
executing the original Blofeld MCU firmware and update/recovery paths.

Nord Lead 2X / NodalRed2x
The device runs an MC68331 model and two DSPs. Its DspBoot helper functionally
receives length/address/data, writes P memory, sets bootstrap register effects
and transfers execution to the downloaded program. The chip bootstrap ROM is
not instruction-executed by that helper. Separate DSP threads are synchronized
to audio progress. A halted-DSP interrupt path explicitly preserves the old
PC/instruction/cycle counters around direct JIT interrupt execution; this is a
specific scheduling abstraction, not evidence of pin/pipeline equivalence.

Waldorf microQ / Vavra
The device also uses DspBoot. Its inspected configuration disables timers used
for DSP-load reporting, sets ESAI clocks explicitly and uses an authored memory
layout. These are concrete functional choices, not a completely reconstructed
electrical board. The shared default memory validator accepts every address;
ordinary memory writes outside allocated backing are suppressed in the release
path. Debug builds additionally diagnose bounds. This behavior does not prove
which Blofeld addresses select RAM, ROM or no storage.

Consequences for Blofeld
- Keep original Blofeld MCU/DSP firmware, original synthesis and instrument
  acceptance. Functional chip bootstrap/peripheral models may replace detailed
  internal mechanisms when their observable transfer/reset/error contracts pass.
- A reserved-address label does not prove a hardware trap, allocated RAM or a
  useful firmware access. Test a no-selected-write decoder explicitly, without
  allocating replacement cells or supplying read data. Trace later reads and
  aliases; successful startup alone cannot distinguish all decoder candidates.
- Derive rates and scheduling constraints from actual firmware dividers and
  musical behavior. Audio-frame/event boundaries can replace irrelevant bus
  phases; preserve notes, envelopes, LFOs, MIDI timing and update state changes.
- Test each simplification across connected startup, playing, persistence and
  update/recovery. Keep unresolved data visible and retain firmware bugs.
