Explicit unknown GPIO peer drivers

PinDrive and DspGpioDrive distinguish four observations. The mask/levels fields
describe known strong peer values. Unknown marks strong drivers whose level has
not been observed. Floating marks explicitly released pins; absent bits remain
unobserved. Known, unknown and floating masks must be disjoint and in range.

A driven-unknown peer makes the shared pad unknown even beside a known local
output or enabled input pull. It cannot be replaced by zero, a weak bias or a
floating observation. Local output-intent getters remain independent of peer
voltages. Architectural MCU output-latch reads retain their existing semantics;
an input read needing an unknown bit fails with its address and PC/CCR context.
DSP pad-dependent data reads and peripheral validation reject unknown levels.
PinOutputs.reduced_drive retains the RDR selection for active GPIO/peripheral
drivers, independently of their latch knowledge. Input/released bits export no
drive strength. This is an output-current selection, not a weak input pull or
an open-drain mode. S12UF32PIMV2 V02.05 specifies about1/6 of full drive for RDR
bits1; no current/voltage winner or safe conflicting-pad level is inferred.
Legacy peer-driven known opposition still fails immediately. No grace period, hidden
buffer gate, automatic acknowledgement or fixed firmware response is introduced.

Reset retains external observations; copies and MCU partial updates preserve
unknown peer bits. Reference MIDI and SHI-return route guards include unknown
drivers when checking explicit route ownership. The text input grammar is
unchanged; this field serves programmatic board coupling.

An explicitly attached, exclusive board pad source can instead separate local
register intent from unknown shared voltage (gpio-pads.txt). It does not change
the default peer-driven path. Actual unknown pin reads and unqualified peripheral
accesses still fail; unresolved intermediate nets cannot qualify a board.

The original request routine creates a direction-before-latch transition in a
declared caller/RAM fixture. Keeping it unknown permits faithful observation of
that intermediate state; it does not establish the actual board wiring, weak
bias transfer, electrical timing or a complete original transaction/boot.

  cmake --build --preset strict --target blofeld-gpio-unknown-driver-test blofeld-gpio-output-test blofeld-dsp-gpio-test
  ctest --test-dir build/strict --output-on-failure -R '^(gpio_unknown_drivers|mcu_gpio_outputs|dsp_gpio)$'

Fixed synthetic expectations cover strong/weak/unknown precedence, independent
local intent, release, reset, partial updates, clone independence, malformed
masks, contextual unknown-read faults and retained known-contention rejection.
Reduced/full selection, unknown/peripheral drivers, release, reset and clone
independence are checked separately. Rebuild matching consumers/archives when
the PinOutputs layout changes; old binaries do not qualify this metadata.
No manufacturer code/data is embedded. No fuzzing or physical traffic runs.
