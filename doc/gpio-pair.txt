Original native request/response pair: component acceptance

original_gpio_pair executes both unchanged original request handlers together
in 32 declared contexts: eight field/source routes, both same-time write orders
and two DSP epoch phases. The MCU executes its original clock prefix and native
GPIO-setup suffix before an own RAM caller with an explicit stack/RAM context.
The DSP uses an own prefix with firmware-derived PLL operands and all 44000 delay
iterations, followed by unchanged original vector/request program records.
This is neither the full startup initializer nor a boot-from-reset test.

The first seven cases use independently declared source value42. The last loads
the entire unique original X-data record containing the startup signature;127
is asserted as an expectation, never written as a host-generated reply. Each
case checks the actual native source-load register effect, MCU return value,
DSP cleanup/foreground return, unchanged source data and program records, whole
MCU flash bytes/knowledge/freshness and healthy native execution.

The shared low-byte GPIO and J0-to-IRQA route is an explicit direct-link
hypothesis. A common1080MHz reference represents the declared nominal MCU30MHz
and DSP54/216MHz rates; instruction completion/vector estimates and selected
tie orders do not establish physical pipeline, synchronization or pad timing.
No PC gate, fabricated IRQ acknowledgement or host reply completes the request.

Local register intent and actual queried pads remain separate (gpio-pads.txt).
Every native pad query must be known and conflict-free. Intermediate unknown
latches, opposed full/reduced outputs and a brief unqualified peripheral-output
selection remain visible in the net audit. The experiment represents that
peripheral selection as an unknown active driver, never a successful peripheral
model. Every case must reject board qualification even after both helpers return.
Successful protocol consumption does not prove the electrical intervals safe.

  cmake --build --preset strict --target blofeld-original-gpio-pair-test
  ctest --test-dir build/strict --output-on-failure -j1 -R '^original_gpio_pair$'

The Python oracle pins the official firmware and all127 record identities before
native execution. It cross-checks case ordering, source addresses/values, complete
query/net audits, preservation outcomes and mandatory board rejection. Eight
fixed evidence corruptions must fail. Manufacturer bytes, detailed source
analysis and traces remain local. No fuzzing or physical traffic is performed.
Full original boot, real board routing/timing, normal MIDI/audio, Desktop/Keyboard
differences and update/recovery/hardware safety retain their separate requirements.

Joint native snapshot and failure recovery

The signature request also supplies12 joint snapshot contexts: both declared
write orders, both epoch phases, and three native event boundaries (two data
writes before the source load, observed output conflict, four writes followed
by actual MCU direction release). Capture composes both native owners, pending
schedule/time, local driver/bias descriptors and audit counters. No caller, PC,
program or source word is reconstructed on restore. The shared own fixture is
original_gpio_pair_fixture.hpp; the32-case request regression retains its trace.

Each context first completes normally. A restored branch must reject both
detached pad queries before explicit fresh attachment. A directed unknown DSP
or MCU observation then reaches an actual native consumer and quarantines the
coupled execution; faulted capture rejects. After changing a separate own RAM
canary, two further joint restores must recover its saved value and replay every
timestamped CPU/pin event, final native CPU state, schedule time and tie count.
Program/source/NVM retention, signature127 and board rejection are checked for
all36 successful returns. There are36 joint restores,72 detached-source refusals,
12 actual unknown-input faults and six fixed oracle-corruption controls.

These are trusted in-process component snapshots. They do not provide a portable
whole-board file, physical recovery procedure, flash/power-loss qualification,
safe conflicting voltages or a successful original boot.
