Original 1.25 MCU bootloader execution fixture

  build/strict/blofeld-boot-test doc/Blofeld_Firmware_V1.25.zip build/strict/Testing/original-boot.trace

The private ZIP is required; CTest explicitly skips this reference check if it is
absent. The synthetic CPU/peripheral tests do not require manufacturer assets.
Keep the generated trace private: it contains manufacturer instruction text.

Fixture and evidence
- Loads the checked, unmodified MCU image and starts at its original reset vector.
  Port E's externally supplied mask 0xfb is driven low. One explicitly supplied
  detector window with 15 PHY edges lets the original lock polling finish.
- CPU instructions execute without elapsed bus/oscillator time. This isolates
  instruction, memory and boot-algorithm behavior; it is not a scheduled board
  model or a hardware-derived pin/clock profile.
- The original code clears all 5120 bytes at 0x1200..0x25ff. The test first checks
  cold RAM is unknown, then verifies every byte after the loop and its final X/Y.
- The original checksum routine reads the application flash, updates its sum on
  the emulated stack and chooses its own success path. No host checksum result
  replaces CPU execution or patches the image. D=0 and restored SP=0x2600 are
  checked at the original application entry 0x8200.
- This fixture reaches that entry after 90314 instructions. The trace records
  instruction text and PC/D/X/Y/SP/CCR before each instruction. Budget exhaustion
  or an unknown access fails the test instead of counting as a boot.

CPU regression found by this check
Ghidra's HC12 indexed-word operand omitted its memory dereference. LDD loaded an
address and STD could assign its base register, corrupting SP and the checksum.
Independent synthetic LDD/STD addressing tests reproduce that error without
manufacturer code. A separately versioned, hash-gated local language patch fixes
the export. See patches/README.txt; installed Ghidra files remain untouched.

Application continuation probe
A separate private diagnostic continues with PE0/PE1 explicitly high, leaving
IRQ/XIRQ inactive. It passes application SCI receive-interrupt configuration,
RTICTL=0x40, RTIE, USB UNCIR/UIMR and MEN setup. After 1672476 completed
instructions through original CPU-counted delay loops, execution fails on the
unknown external PTU0 input (register 0x0278, bit 0, PC 0xb98d). No elapsed
bus/oscillator time or USB decoder events are supplied. The full private trace
including the attempted failing instruction has SHA-256:
  dc95a12e8b706d71a3bb2472f753e946de804536895ad1785eedb84109625d00
The MCU data sheet identifies PU0 as general GPIO or a CF/ATA signal depending
on configuration; its Blofeld board connection is not established by that fact.
The default model leaves this input unknown; it does not supply a ready level.
The image and CPU loop state are not patched or bypassed. This remains an untimed,
unverified pin fixture; no application or complete-board boot is inferred.

Original MCU sender experiment
  ctest --test-dir build/strict -R '^original_mcu_sender$' --output-on-failure

The optional regression checks the private ZIP's SHA-256 before execution and
starts the unchanged MCU image at its reset vector. PE0/PE1 are explicitly high
and the same detector window is supplied. At the PU0 poll, a register read first
verifies that the unobserved input still faults with its address and input mask.
The experiment then observes PU0 low for two executed polling iterations and
high for the third. PB3/PB5/PB6/PB7 are explicitly observed low for PORTB reads.
These are controlled laboratory inputs, not measured board levels or defaults.

The original application executes its own delay loops, loads its own flash data
and writes PORTB. The observer captures PB1 as candidate active-low selection,
PB2 as clock and PB4 as serial data. It records only stable selected falling
edges, requires 24 per frame and checks every captured word against original
flash. The resulting 97 frames contain the length/address, all 94 DSP first-stage
words and one additional trailing word. Exactly 7275 PORTB writes are required.
With the two low polling iterations, this takes 1856593 MCU instructions.
No host program-memory writes, CPU-state patches or loop skips supply this data.
The private trace records PORTB writes/pads and CPU snapshots at the gate and
after transmission; it is written under build/strict/Testing/.

The first selection also lowers the previously high clock in the same PORTB
write. The observer records this unordered transition without treating it as a
data edge. It does not resolve physical transition order or feed a DSP receiver.
The current SHI model rejects simultaneous SS/SCK transitions. DSP56371 data
sheet Rev. 4.1 section 12, table 20, item 27 requires 10 ns from SS assertion to
the first SCK edge in CPHA=1 slave mode. The GPIO write alone supplies neither
pad skew nor that interval. Board routing, edge order and reset/clock behavior
need qualification before direct combined boot can be claimed. The separate
DSP fixture still uses host pin events (dsp-core.txt); no full boot is proven.

Original application interrupt continuation
A private continuation supplies PU0 high directly after its direction is released,
PB3/PB5/PB6/PB7 low, and an explicit USB decoder state: full speed, not enumerated,
not reset and not suspended. With
no elapsed peripheral time, the MCU waits for RAM counter 182e. A second fixture
supplies one configured RTI oscillator period at alternating visits to that wait,
allowing an interrupted load to execute before the next delivery. The original
handler at 88a5 increments the counter and scans GPIO; 255 interrupt entries and
255 RTI returns release the wait at 86a4 after 2266847 completed instructions.
No host counter writes or CPU-state patches cause that transition. Continuing
stops after 2295981 instructions at PC 8ad2 on PORTB input mask 16 (hex), which
has become unknown after GPIO direction changes. This is an explicit untimed
interrupt experiment, not a calibrated oscillator/CPU ratio or complete boot.

Limits
Reaching an application entry does not establish a complete Blofeld boot. DSP
loading, NAND/ROM assets, scheduled clocks/interrupts, actual MIDI/audio, update
and recovery execution, persistence and power-loss behavior still need coverage.
Desktop/Keyboard pin differences and comparison with stock hardware are pending.
