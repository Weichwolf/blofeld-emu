Native serial MIDI output

The reference Board optionally observes one fixed MCU output pad:
  midi-output PR3
  midi-output PS5
This is a declared SCI MIDI route, not automatic Desktop/Keyboard profile wiring
or host-visible USB-MIDI. The ordinary MIDI input routes remain independent.

MidiSerialReceiver passively decodes 8-N-1 at 31250 baud. The caller must report every
wire change and advance through pending bit centers. Changed levels take effect
before coincident samples; contradictory same-tick observations and reversed
time reject. Fractional sample centers round from the frame's absolute start,
without accumulated bit-period rounding. A byte is published at its known high
stop center, with original start/stop-sample timestamps. Unknown idle supplies
no edge; unknown active levels and invalid framing quarantine the decoder.

McuMidiOutput reads resolved PR3/PS5 pads, retaining unknownness and conflicts.
It never consumes a CPU register, drives a wire or advances device clocks.
Its 256-byte value-owned ring retains pending output and partial serial state.
Overflow fails visibly with operation, pad address/mask, PC, CCR and ticks;
no byte is silently dropped. The capacity is an internal bounded queue choice,
not an assumption about a host kernel's MIDI pool or grants.

Board observation covers MCU cycle starts, completed native writes and final
operation boundaries, including POR and WAI. Configured TX pads cannot also be
external drives, DSP return lines or loopback destinations. Optional capture
belongs to the whole trusted Board checkpoint. Queued and partial bytes restore
with native owners; external MIDI sessions must observe the changed restore
revision and retire instead of replaying already delivered host output.

midi_output_window() reports owner/revision, time, configuration and counts.
pop_midi_output() retires one actual captured byte at an inactive healthy Board
boundary. An unconfigured output rejects; an empty configured queue supplies no
response. Consumers must drain the bounded queue and handle delivery failures.

Tests: midi_serial_receiver, mcu_midi_output and reference_midi_output cover
literal wire expectations, fractional timing, contiguous frames, partial copies,
resolved SCI pads, queue bounds and native reset/WAI/checkpoint integration.
Both sanitizer configurations pass these three scopes plus reference_pipeline
and reference_checkpoint, with actual executable identity and strict compiler,
format, clang-tidy and ELF checks. See midi-output-reference.json for source
hashes and the ten native cases. This work does not establish normal original
instrument startup, firmware replies, host MIDI output or USB enumeration.
The subsequent HostMidiSession adapter delivers these native bytes to its owned
sequencer port; authored reset/SCI and independent kernel-record evidence is in
host-midi-session.txt and host-midi-output-session-reference.json. That separate
adapter qualification does not establish original-instrument replies or USB.
Original-firmware bidirectional transfer and all documented instrument functions
remain acceptance requirements in coverage.txt and function-acceptance.tsv.
