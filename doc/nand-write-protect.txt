NAND held write-protection input

The developer board profile accepts an explicit active-low WP input on either
backing. The timing selector and WP option may appear in either order:

  nand-image j "/path/to/cold.bfnand" functional-protocol wp high
  nand-store j "/path/to/live.bfnand" wp low

Omitted WP remains unknown. high declares an inactive protection input; low
asserts protection. Missing/unknown levels, duplicate WP options and unsupported
timing selectors fail. The held source is applied before constructing the NAND
peer, through the existing protocol/store input. It adds no guest instruction,
clock delay, physical GPIO route or mutable cell metadata. In-memory checkpoints
retain the protocol input; durable files retain cells, not a board wiring source.

This is an explicit functional board hypothesis. Original Port-F upper data
writes do not establish a direct or inverted PF10-to-WP route. Existing unknown
input, block validity/protection, program-history and cell-transition checks
remain independent. The regular Board still uses an unqualified cell profile:
wp high alone cannot complete programming or erase, invent a successful status,
or qualify original preset saving, updates or recovery.

Targeted regression scope: both backing parsers preserve unknown/default and
explicit high/low inputs; authored native GPIO erase sequences refuse unknown
or low WP at setup. Explicit high reaches confirmation and still refuses the
absent cell model. Refused operations preserve the durable image. Existing
native reset/Busy, strict timing refusal and joint-restore cases remain covered.
Both groups pass with ASan/UBSan and strict LLVM 19 quality checks. No fuzzing.
