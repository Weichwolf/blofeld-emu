Standalone runtime interface: required behavior

Launching without profile arguments must select Blofeld Keyboard. --desktop selects
Blofeld Desktop. Do not add a blofeld-cli companion or a separate --keyboard
option. The emulator runs as a device process, without an interactive CLI.
Both profiles must execute the unchanged original 1.25 firmware and their actual
required peripherals. Normal operation presents the selected device through
MIDI and/or an actual host-visible USB-MIDI interface, including original
control, SysEx, sample/update, reset and failure behavior.

The emulated analog outputs supply audio from the original DSP to the normal
session audio host and default output, as an ordinary audio application. PipeWire
is suitable when it is the host's audio service; the runtime must not require
exclusive access to an ALSA hardware device or replacement of the user's audio
service. Host audio buffering/device negotiation stays outside MCU/DSP/board
behavior. No host synthesizer substitutes for the firmware's audio generation.

Host portability is a requirement for both audio and MIDI. Query capabilities,
read back actual negotiated settings and keep preferences distinct from grants.
Adapt host buffering/packetization to those grants; report unsupported formats,
lost events and service failures visibly. Never change emulated clocks, PLLs or
MIDI baud to accommodate the host. Test smaller/different grants and refusal
paths. Kernel/service behavior on this development host is not a universal
limit. The native session adapter now validates client PCM/rate/layout and actual
buffer grants, observes device/suspend state and starts its worker from actual
target dimensions (host-audio.txt). Private corked-stream route/suspend controls
are qualified under Pulse17; PipeWire1.4.2 has separate corked-route, actual-grant
and finite-worker checks, including a server-enlarged target distinct from the
capacity preference (host-audio.txt). PipeWire suspension, active device
moves, rewinds and normal profile/status binding remain open.
host-midi-port.txt records the separate sequencer evidence.

USB remains MIDI-only. Do not add USB Audio descriptors, endpoints or a virtual
USB sound card. Host audio playback is independent of the emulated USB link.
Waldorf confirms that Blofeld USB carries MIDI and cannot stream live audio:
  https://waldorfmusic.com/faq-blofeld-keyboard/
PipeWire host/client/device routing is described at:
  https://docs.pipewire.org/page_overview.html

Existing CLI reference runners, inspection, trace/WAV export and samples commands
are optional development tools. They are not the normal-operation interface and
do not establish complete boot, device enumeration or live audio. Source and
reference artifacts remain separate; manufacturer firmware/assets stay local.

Development processes can select a persistent virtual MCU unit with
--device-state /private/existing-dir/unit.bfnvm (device-identity.txt). This is
separate factory/NVM ownership, not a working normal device profile. The first
creation allocates its own serial; later starts use the complete saved state.

Display snapshots and live GUI access use packed 1-bit PBM/text files below
$XDG_RUNTIME_DIR/blofeld-emu/. Atomic replacement and directory change events
permit live GUI refresh at complete-frame publication boundaries, analogous to
a software display swap. PNG is for saved screenshots; see display-export.txt.
The separate native GTK Blofeld Display viewer only consumes this export; it
waits for available frames without starting or controlling the emulator.

Current evidence and missing requirements
coverage.txt retains the full acceptance scope. Keyboard/Desktop normal startup,
complete original boot, host USB-MIDI enumeration and original firmware audio
remain unqualified. The separate session adapter and bounded AudioRuntime worker
have native DSP/ESAI-to-private-service tests (host-audio.txt, audio-runtime.txt).
The reference board can bind that worker without changing native state/ticks;
restore retires the external stream. Normal startup/profile wiring, sustained
original firmware audio remain pending. Directed private PipeWire playback
does not establish that runtime. Conditional
original MCU/DSP MIDI/F4 fixtures and serial PCM/WAV gates are component evidence.
The reference API also admits owned ALSA sequencer input through a common-time
SCI wire during POR/WAI; restore retires its host session (host-midi-session.txt).
Its explicit SCI transfer hypothesis does not establish normal firmware reception.
Real hardware equivalence, update/recovery and realtime behavior still require
their own complete validation.
