Host-visible USB-MIDI requirement and transport boundary

blofeld-emu must present an actual USB-MIDI device to the host USB subsystem.
Original descriptors, control requests, configuration, MIDI IN/OUT, SysEx and
sample transfer must go through the emulated USB peripheral and unmodified
firmware. A virtual ALSA port alone does not satisfy this requirement. Wine
Spectre must be qualified against that virtual USB device through the host MIDI
driver; successful detection alone does not establish functional communication.

Current state
McuUsb models registers, buffers and explicit decoded transactions. Native own
CPU/ISR/endpoint tests and conditional original reset/configuration/descriptor
tests exist. There is no live host USB integration or functioning USB-MIDI device today.
The MCU-backed transfer queue and USB/IP transfer-stage framing are implemented
and tested with own native IRQ/descriptor fixtures (usb-host-transfers.txt).
MCU-backed descriptor capture and USB/IP discovery/import framing are implemented
separately (usb-discovery.txt). A bounded nonblocking loopback listener/session
exists (usbip-session.txt). Explicit reference-board/CLI binding has own runtime
tests (usb-runtime.txt); kernel attachment and actual USB-MIDI remain absent.
Actual SET_CONFIGURATION/SET_INTERFACE SETUP decoding and pending-status NAK are
modeled; the former executes the original configuration ISR and replays through
RTI/WAI. Automatic status completion after DONEECRU is still an explicit failure
until its endpoint register/interrupt effects are qualified. No host status
success follows merely from firmware acknowledging the configuration interrupt.
--midi-device is a read-only legacy RawMIDI input, with no output or USB-device
enumeration. The editor's XML/WAV commands are offline functionality.

Original enumeration still stops when FFD2 acknowledges SETUP before reading
USTB: address 0x033f at PC 0xbc3d. The current peripheral specification declares
the setup buffer valid only with SETUP set. A two-SETUP overrun condition can
queue original descriptor data but does not complete normal enumeration.
Original MIDI endpoint descriptions also use NISOF=2 where the manual specifies
zero. These conflicts remain visible; usb-reset.txt records the exact evidence.
Do not synthesize descriptors, mask reserved fields, retain invalid bytes without
evidence or manufacture a successful status phase to make host attachment pass.

Backend requirements
- Keep host transport independent of MCU/DSP execution. Supply real request/data
  events and return only bytes/completions produced by the modeled peripheral.
- Preserve control setup/data/status phases, short packets, zero-length status,
  bulk IN/OUT, pending NAKs, errors, cancellation, reset/disconnect and retries.
  Reconcile a host URB's abstraction with hardware ACK/PID ownership explicitly.
- Obtain advertised identity/configuration from the original firmware/device
  model. Do not use a host-side fake Blofeld responder or route to a host synth.
- Run the emulator as the regular user. Host-controller provisioning must remain
  separate from application startup; do not load modules or alter system USB/MIDI
  routing automatically as a routine test.
- Prove actual host USB enumeration/class binding, bidirectional own MIDI/SysEx,
  original receiver replies and Spectre transfer/cancellation/failure behavior.
  Retain remaining boot, update/recovery, timing and device-equivalence limits.

Linux candidates are a userspace USB/IP server imported by vhci_hcd, or a gadget
backend with an available UDC/virtual controller. USB/IP exports URBs over TCP;
the importing host runs the device's normal driver. Raw Gadget exposes requests
to userspace but is documented as a debugging interface, not a production
backend. Reset/address/configuration semantics must be qualified before selecting
and exposing a usable Blofeld backend. USB/IP components exist; the board/runtime and host-controller integration is
not qualified as a usable original-firmware USB device yet. Reference runtime
admission/lifetime is documented in usb-runtime.txt.
The controller's ENUMD flag means completed PHY chirp/speed negotiation; it does
not establish successful host descriptor/address/configuration enumeration.

In Wine 10 the ALSA MIDI driver handles MIDI and SysEx via the ALSA sequencer.
For host USB-MIDI, this yields the intended path: Spectre -> Wine MIDI -> host
USB-MIDI driver -> virtual USB transport -> MCU peripheral/original firmware,
and back. Wine does not need a physical device for that eventual virtual path.
This architecture is not evidence that current Spectre/emulator transfers work.

For a connected keyboard, the target route is keyboard MIDI output -> host MIDI
routing -> the virtual device MIDI input. Once Linux USB-MIDI exposes the device
as ALSA sequencer ports, PipeWire can bridge and connect these ports. A separate
emulator-owned MIDI hub is not required. This routing is not yet qualified here:
the emulator has no host-visible USB-MIDI port today. MIDI traffic still follows
the modeled peripheral/original firmware rather than a host synthesizer.
